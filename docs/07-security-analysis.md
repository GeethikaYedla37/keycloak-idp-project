# Security Analysis and Threat Model

## 7.1 What this system is trusted to do

Every downstream application (or identity-aware proxy) that trusts this IdP
is implicitly trusting that:
1. Only Keycloak can mint a validly-signed JWT for this realm.
2. A token's `groups` claim accurately reflects the subject's real group
   membership at the time of issuance.
3. Tokens expire and cannot be replayed indefinitely.

If any of those three trust anchors break, every downstream system that
relies on this IdP is compromised simultaneously — which is exactly why the
IdP is the highest-value target in a Zero Trust deployment.

## 7.2 Assets

| Asset | Why it matters |
|---|---|
| Keycloak admin credentials | Full control over every realm, user, and client |
| Realm signing keys (JWKS private key) | Whoever holds this can forge valid tokens for any user |
| Postgres database | Contains user records, hashed credentials, client secrets |
| OIDC client secrets | Allow impersonating a registered application when requesting tokens |
| Issued JWTs in transit/at rest in browsers | Bearer tokens — possession equals access until expiry |

## 7.3 STRIDE Threat Model

| Threat | Example | Mitigation implemented in this project |
|---|---|---|
| **Spoofing** | Attacker impersonates a user | Password + enforced MFA (TOTP) for privileged (`Admins`) group |
| **Tampering** | Attacker modifies a JWT's claims (e.g. adds themselves to `Admins`) | Tokens are signed (RS256 by default); any modification invalidates the signature, and relying parties must verify it against the realm's JWKS |
| **Repudiation** | User denies performing an action | Keycloak retains login/event history in its admin console (events must be enabled per realm) |
| **Information Disclosure** | Client secret or admin password leaked | Client secret is generated by Keycloak (not hand-picked), kept out of source control via `.gitignore`, injected via `appsettings.Development.json` at setup time |
| **Denial of Service** | Credential-stuffing / brute-force login attempts | `bruteForceProtected=true` enabled at realm creation, which locks accounts after repeated failures |
| **Elevation of Privilege** | Low-privilege user tries to access an admin-only resource | Downstream apps/proxies are expected to authorize based on the `groups` claim, not merely on "is authenticated" |

## 7.4 Known Weaknesses in This Deployment (dev configuration)

Being transparent about this matters more than pretending the setup is
production-hardened:

- **HTTP, not HTTPS.** Keycloak runs on plain `http://localhost:8080` for
  local development. In transit, tokens and credentials are unencrypted.
  Production deployments must terminate TLS in front of Keycloak.
- **`start-dev` mode.** Keycloak's dev mode disables some production
  safeguards (e.g. it doesn't require an explicit hostname configuration).
  Production requires `start` with `KC_HOSTNAME` properly set.
- **Static admin password in `docker-compose.yml`.** Fine for a local lab,
  unacceptable for anything reachable outside localhost — should be
  supplied via a secret store or environment injection, and rotated.
- **Bearer tokens have no additional binding.** A stolen access token can
  be replayed by anyone until it expires. Mitigations like short token
  lifetimes, token binding, or mTLS are not configured here.
- **No centralized audit log shipping.** Keycloak's login events exist but
  aren't exported anywhere durable/queryable in this setup.

## 7.5 What This System Does NOT Protect Against

- Compromise of the end-user's device (a keylogger capturing the password
  still defeats the first authentication factor).
- A malicious or compromised downstream application that *correctly*
  validates tokens but then abuses the access it legitimately receives.
- Social engineering of the identity administrator to grant excess access.

Zero Trust reduces the blast radius and forces continuous verification — it
does not eliminate the need for endpoint security, secure coding in relying
parties, or organizational security awareness.
